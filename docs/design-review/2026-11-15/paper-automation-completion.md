## P1 — Explicit source refresh for normal Web paper runs

**Current behavior.** The reviewed Web preview freezes its selected union. `WorkflowRunConfiguration.WriteAsync` deliberately passes no screen query or wishlist ID to `RunConfigWriter`; `PaperDiscoverySessionFactory` therefore uses the fixed accepted symbols. Editing a stock group or rerunning a screen does not update that run. The read-only scheduled Finviz archive is independent.

**Proposed behavior.** Add one explicit run option, **Stock membership: Fixed at launch / Refresh selected sources**, with Fixed at launch selected by default. Show the chosen mode in preview, confirmation and run detail. Fixed remains a useful deliberate experiment choice, not a compatibility layer. Refresh means the same selected stock-group ID and the same frozen normalized Finviz query, never whichever group happens to be the default later. Both means union, deduplicated by ticker while retaining separate source observations. A saved-screen filter edit requires a newly reviewed run; membership returned by the frozen query may change.

Reuse the normal preview, immutable universe receipt, run configuration writer, `PaperDiscoverySessionFactory`, `DurableDiscoverySession` and existing shared 60-second refresh cadence and 180-second source expiry for both source types. Resolve source descriptors on the server at preview. Bind mode, canonical group ID, normalized query/hash and all selected source descriptors into preview and start idempotency/provenance, including a selected source that returned no members while the other source was nonempty. Start uses that bound snapshot; it may not accept substituted IDs or a changed query from confirmation. Keep the current refusal for an entirely empty launch in this first version; do not start an unreviewed empty polling job.

Finviz refresh membership means symbols actually observed in a validated bounded response, not proven complete membership of the whole remote screen. Reuse receipt capture and strict structural parsing for this path; the permissive parser that ignores malformed lines cannot authorize new entries. Invalid/truncated/partial or ambiguous zero/header-only responses are failed/degraded and confer no entry authority. Only explicit provider evidence can establish a genuinely empty remote result. A genuinely empty editable stock group can coexist with another valid source. Absence means absent from the current bounded observation, not proof that the symbol no longer matches Finviz. The scheduled archive worker stays separate.

Refresh records retain actual observation time, expiry, success/failure and member provenance. A stale or failed source grants no entry by itself. An unexpired healthy overlapping source can still qualify the symbol. On removal from all healthy sources, fence new admissions and unsubmitted opening commands, retaining held and working symbols for normal exits/protection. Do not sell merely because a symbol left a group and do not cancel an ambiguous linked group. Recheck effective membership at decision, reservation and first POST. On restart, refresh selected sources before permitting new entries. Reuse the first-dispatch transactional predicate in `SqliteOrderIntentRepository.PaperDispatch`: exact job lease/entry stop, `(run ID, candidate ID, Triggered version, symbol)`, current discovery aggregate, active source IDs, expiry and observed source failure. Factor that same predicate into the reservation transaction before portfolio risk reservation and the candidate Consumed compare-and-swap. No additional intent membership field is needed. The existing first-POST fence remains authoritative. A removal committed before that fence refuses submission; this cannot detect a provider-side membership change before its next refresh or retract a request already past the dispatch fence. Newly added symbols need their own complete warm-up and strategy qualification, with bounded existing worker/stream capacity; a warm-up completion cannot revive a removed observation. Preserve source descriptors, mode and fences through restart and build-continuation rules.

The launch snapshot remains immutable evidence. Later membership is a sequence of separately timestamped observations, never an edit to that snapshot. Refresh follows the existing per-source/run cadence inside the durable leased paper job, serialized by the discovery session instance. This is not a separate durable per-source lease or global cross-run deduplication, and refresh is not driven by charts or tickers. Retain current bounded discovery limits; show failed/retrying/removed/expired reasons in existing health and decision audit. This does not create a daily auto-start schedule, register a strategy or change a screen/group.

**Affected areas.** Paper Razor/API request and preview contracts, `UniverseCandidateWorkflow`, `WorkflowRunConfiguration`, `RunConfigWriter`, paper discovery and run-detail projection. Reuse journal/repository storage where its existing source receipt contract suffices; any missing canonical source descriptor must be explicitly persisted with the preview/run rather than reconstructed from member rows.

**Acceptance.** Fixed-mode exact behavior; group/screen/both union and overlap; one genuinely empty selected source; malformed/truncated/ambiguous-empty screen refusal; bounded membership labels; totally empty refusal; source substitution/query edit between preview/start; idempotent restart; added symbol warm-up; removal during warm-up and before POST; source failure/stale expiry; open-position exits after removal; unchanged account and strategy authorization gates; bounded request counts. Actual source-refresh acceptance uses a separately owned synthetic source/DB. No mutation test uses the user's stock groups or broker.

## P2 — Stop hours-late entries for next-open strategies

Add a shared, side-effect-free, versioned policy `next_regular_open_window` for an explicitly opted-in daily setup that intends to execute at the next regular open. The run freezes a finite positive grace duration. There is no automatically chosen operational grace; five minutes is a fixture example, not a claimed trader standard. An actual strategy/run needs an approved value and exact new identity when its economic behavior changes.

Derive the intended session from the authoritative exchange session immediately following the completed setup source session, independent of host start, receipt time or retry. The permitted command interval is `[regularOpen, min(regularOpen + grace, regularClose))`. Before it, wait; at or after its exclusive end, journal `entry_window_missed` and make no new opening submission. A late setup receipt or required confirmation does not move the window to tomorrow. Record missed-window evidence once per run/strategy identity/symbol/setup, including a setup already expired when first observed before candidate creation; repeated polls do not append identical refusals. Missing verified calendar/timing evidence refuses entry. Exits and protection are unaffected.

Reuse `PaperDecisionCalendar`, `ExchangeSessionCalendar.NextTradingSession` and the actual economic open from `FineExecutionTiming.SessionOpen`, not a daily candle's midnight timestamp. Bind candidate expiry and durable `DispatchExpiresAtUtc` to the policy end. First broker POST uses the existing atomic expiry check. Already attempted/ambiguous orders are reconciled/adopted before any new-submission logic. This is a submission deadline; a previously accepted working order can still fill afterward. Cancelling that remainder must use the existing protected cancellation workflow and must not be represented as a guarantee that it cannot fill.

New backtest runs opting into this policy use the same bounds at causal modeled command/activation time. A replay adapter that cannot prove that time refuses the combination. Do not reinterpret old publications, change setup close timing, or add this daily-open policy to unrelated intraday strategies. The run detail and comparison report show intended open, exclusive window end, setup/availability/confirmation time, actual attempt/fill and missed reason in New York, Berlin and UTC.

**Acceptance.** Open/end boundary, holiday/weekend, DST and early-close calendars; late receipt/confirmation; start before/after window; no next-session slide; retry/adoption across cutoff; daily bar midnight versus economic open; matching paper/replay admission at fixed timestamps; exits after expiry. No economic replay is started to approve the mechanism.

## P3 — Explicit account-loss policy in new backtests

Reuse pure `AccountLossLimitPolicy.Observe/Refusal`, not the operational broker/SQLite guard. New run input freezes enabled state, daily/weekly/peak thresholds and the versioned five-minute sampled policy/evidence basis described below; the first version does not offer an arbitrary observation cadence. Existing published results are immutable. Ordinary unchanged replay settings keep the existing behavior; reports explicitly disclose whether account-loss limits were applied. No global threshold or operational account baseline is changed by this work.

Support only long-only `ExecutionReplayPolicy.DailyRthFiveMinuteV1` (`daily-rth5m-nextslice-ioc-v1`) through `BacktestRunner.FineExecution.ValidateFineExecutionPolicy` and `ChronologicalBacktestExecutionCoordinator`. Ordinary native daily, SIP and intraday replay paths reject the enabled option. Sample at every authoritative completed regular five-minute boundary and use the latest completed sample before admissions. Require compatible exact held-symbol slices with `AvailableAtUtc == EndUtc`. Use the authoritative last regular close after all held quantities and fees are applied for daily baseline evidence and the New York calendar for week boundaries. An unavailable close leaves the baseline invalid until verified. A prior verified close supplies a baseline denominator, not a fresh current-session mark. At the verified official session open (normally 09:30 New York), flat cash can be sampled; existing nonzero exposure without a fresh current-session completed mark yields `loss_mark_unavailable_at_open` and refuses that candidate. Do not peek at the first five-minute close or shift a next-open candidate to 09:35. Freeze simulated `MaximumSnapshotAge = 5 minutes` inclusive, with `RequestedAtUtc == ObservedAtUtc` at a verified completed boundary or flat official session open, never the present-day host clock. Marks must belong to the current session. Explicitly distinguish this sampled mechanism from the live 60-second freshness check. Any other missing required slice/mark makes the observation unavailable and blocks new entries. Never silently forward-fill or substitute realized P&L.

Equity is causal simulated cash plus signed filled quantities at verified marks, including partial fills and fees. Completed-trade P&L alone is not equity. For an isolated new account, label its synthetic flat starting-capital anchor explicitly; never claim historical broker equity. At each boundary, batch all symbols: apply prior-slice fills/fees already modeled by the coordinator, update all held-symbol close marks, evaluate one account sample, latch breaches, then consider commands scheduled for the next slice under the existing stable ordering. Do not latch transient per-symbol intermediate equity or erase fills already modeled before the check.

This adapter's opening commands are IOC. Prior-slice remainders must already be terminal at the boundary; assert that no working IOC remainder remains, then complete the simulated cancellation-sweep transition and clear `CancellationSweepPending` before applying the shared refusal/reset rules. Suppress unissued entry plans after a breach. Failure to prove the terminal remainder leaves the sweep pending and new entries refused. This first version does not simulate cancellation of resting/GTC parents and does not claim intrabar or broker loss-policy parity. Preserve risk-reducing stops/exits. Daily/weekly resets and observed-peak latching reuse the pure policy; reviewed intrarun peak resets are outside this version. Advance authoritative flat-calendar ticks cheaply even without active orders/candidates so baselines and period resets cannot be skipped by the coordinator's current early return. No repeated historical scan.

Stream the adapter chronologically with current filled positions, pending commands and baseline/latch state. No repeated full-history scans, original artifact rewrites, provider calls or new economic experiments are part of implementation. Add manifest/report fields and exact policy identity through the existing config/parser/result routes.

**Acceptance.** Inclusive 2%/4%/10% fixture boundaries, unrealized/partial-fill/fee losses, recovery while latched, daily/weekly/holiday reset, peak latch, missing mark, no-candidate periods, overnight exposure without an opening mark, flat opening cash, simulated sweep completion and period recovery, mixed-symbol same-time order independence, fills/fees before boundary checks, terminal IOC remainder and next-slice refusal, isolated books, unsupported paths, and exact disabled-policy replay parity. Independent plan and code/design review precede any release.

## P4 — State the linked-order provider limitation honestly

Current code already creates simple opening orders, installs separately owned protection after verified fills, safely cancels proven standalone remainders, and journals linked/ambiguous groups for reconciliation. Preserve those controls and their existing tests. Do not create a duplicate cancellation mechanism merely to mark RSK-02 complete.

A linked remainder can still fill during review. Alpaca's documented linked-order semantics do not provide an atomic cancel-with-continuous-protection primitive. A read-check-cancel sequence cannot establish that guarantee. Mark this capability **unsupported: broker operation unavailable**, with the existing entry fence and explicit review/remaining-exposure status. Final review must verify current UI/audit explains that the remainder may still fill, exact stop coverage/flatness is checked, and uncertain groups are not automatically deleted. If those explanations/tests already satisfy the contract, record containment accepted without new code. A different broker handoff or risk acceptance needs its own concrete design and authorization.

[Alpaca order documentation](https://docs.alpaca.markets/us/docs/orders-at-alpaca) was checked on 15 November. No implementation can truthfully close a provider-side atomic guarantee that is not available.
